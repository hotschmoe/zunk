# Zunk v0.9.0 -- File dialog bridge (issue #14)

**Audience**: Teak maintainers.
**Zunk version**: 0.9.0 (additive; no breaking changes).
**Tracking**: closes <https://github.com/hotschmoe/zunk/issues/14>.

## TL;DR

Teak's `Host.requestFileDialog` no longer stays `.pending` forever in
wasm builds. Zunk now auto-resolves `__zunk_request_file_dialog` to a
browser file-picker shim and calls back into the wasm export
`__zunk_file_dialog_result(id, ptr, len)` exactly as teak's `wasm.zig`
already expects -- zero changes required on teak's side.

Tag to pin once this is merged: **v0.9.0**.

## Wiring summary

```
teak wasm.zig                 zunk JS bridge                 browser
-------------                 --------------                 -------
requestFileDialog(filter)
  externs.__zunk_request_file_dialog(id, mode, name*, pat*) ->
                              parse pattern -> { types }
                              window.showOpenFilePicker / Save
                                                            user picks
                              await promise ----------------+
                              write handle.name into
                                __zunk_string_buf_ptr region
                              exports.__zunk_file_dialog_result(id, ptr, len)
__zunk_file_dialog_result
  -> slot.state = .resolved_ok
pollFileDialogResult(id)
  -> .ok = path
```

## What zunk now does

- New exact-match entry in `gen/js_resolve.zig` for
  `__zunk_request_file_dialog`. Resolves under the `dom` category.
- The `__` short-circuit was reordered so an explicitly-registered
  `__zunk_*` import wins over the silent internal stub. Unknown
  `__*` imports still get the stub, so this only affects names we add
  to `exact_db`.
- Path bytes ride in the existing 64 KB `__zunk_string_buf_ptr` region
  -- no new export was needed on zunk's side. The buffer is reused by
  any subsequent JS->Zig string call, so consumers (teak's existing
  `__zunk_file_dialog_result` already does this) must copy out
  synchronously.
- Browsers without the File System Access API (Firefox/Safari today)
  fire `console.warn` once per request and resolve the slot via
  `path_len == 0`, which teak already maps to `.cancelled`. Ship a
  `bridge.js` override if you need an `<input type="file">` fallback.

## What you DO NOT need to change

- `extern "env" fn __zunk_request_file_dialog(...)` -- the bytes-on-the-wire
  match what zunk emits (id, mode, name*, name_len, pattern*, pattern_len).
- `pub export fn __zunk_file_dialog_result(...)` -- zunk's JS calls this
  through `wasm.exports.__zunk_file_dialog_result` exactly as written.
- The Win32-style pattern format -- zunk's bridge splits `;`, filters
  for entries starting with `*.`, and maps them to `{ "application/
  octet-stream": [".zig", ".zon"] }` for the picker's `accept` field.

## Gesture-gating verification

The picker only opens if the request is dispatched inside the browser's
transient activation window (~5 s after a click/keydown). Teak's flow
already satisfies this: input event -> input.poll() flush -> wasm
frame() -> update() Msg dispatch -> requestFileDialog. That whole chain
runs inside the next `requestAnimationFrame` after the click, well
within transient activation. If teak ever moves the dispatch to a timer
or async tick the browser will throw `SecurityError` and zunk will hit
the cancel path; the demo `examples/file-dialog-demo/` exercises the
happy path so you can sanity-check the chain locally.

## Out of scope (still)

- File **contents**. Browsers only expose `handle.name`, not the path or
  bytes. A follow-up issue should add `__zunk_read_file_handle` (or a
  streaming variant) so teak can actually load the chosen file.
- `multiple: true` selection. The bridge passes `multiple: false`.
- Path length above 64 KB. Bytes get clamped to the exchange-buffer
  cap, which already exceeds teak's 1024-byte slot, so this is academic.

## Smoke test

```
cd examples/file-dialog-demo
zig build
zunk run
```

Opens a canvas with two buttons. Clicking either triggers the picker;
the resolved filename renders inline. The example mirrors teak's
slot-table shape (single slot, 1024-byte buffer, status enum) so it
also doubles as the integration contract.
